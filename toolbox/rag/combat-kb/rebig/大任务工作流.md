# 大任务工作流 — 遇到大的任务该怎么搞

> 核心理念:**分块执行、后台执行、突破执行,贯彻到底。**
> 基于猫和老鼠(mhls)逆向实战复盘。先盘清、再拆解、先打通、后攻坚、边干边沉淀。

---

## 0. 总原则

| 原则 | 说明 |
| --- | --- |
| **分块执行** | 大任务拆成独立小块,每块可单独验证、单独失败、单独重跑 |
| **后台执行** | 长任务写脚本丢后台,前台永远有活干,互不阻塞 |
| **突破执行** | 遇到墙(反调试/性能死路/缺数据)就针对性突破,不绕开不放弃 |
| **观察进程** | 动手前先观察目标进程状态(存活/稳定/前台),确认健康再操作;操作中持续观察 |
| 关键路径优先 | 所有支线服务于"解锁一切"的节点 |
| 证据链 > 猜测 | 每个结论有锚点(反汇编地址/黄金样本/实测),写下来 |
| 对症下药 | 盲目扫描是最后手段;先找"典型标识"和"已知两端" |
| 时间盒 | 每环节设时限,超时换路,不恋战 |

## 1. 分块执行(怎么拆)

### 拆块规则
- **一个脚本只做一件事**,输入输出清晰,参数化(路径/范围/超时做命令行参数)
- 先跑小样本(1 个文件、1 轮、K=8 约束)验证,再放大
- 每块有独立验收标准(可测量,如"解密命中 luac 头 100%")

### 分区执行(数据侧的分块)
- 大数据按区抓取:内存按段分(so 数据段/堆/匿名段)、文件按批分
- 先探测(每段抓 64KB 找特征),命中再全量——避免盲目抓 GB 级数据
- 每区独立落盘、独立分析、独立命名(seg1/seg2/heap192/...)

### 分块推进示例(mhls)
```
[密钥] ← 命门
   ├─ 块A: 静态候选验证 (1833/690/25万, 全灭 → 结论: key 非可打印 16B 串)
   ├─ 块B: 数学求解 (Z3 单字约束 38s 超时 → 结论: 死路, 不再投入)
   ├─ 块C: 动态 hook (反调试墙 → 突破: 换端口/改名 → 成功注入)
   └─ 块D: 内存抓取 (纯 dd 零注入, 定位 XXTEAUtil/明文脚本)
```
**每块失败都产出结论**(不是白费),失败结论 = 排除法,缩小搜索空间。

## 2. 后台执行(怎么跑)

### 规则
- **>1 分钟的任务一律后台**:run_background 或 nohup,结果落盘,不依赖终端
- 脚本必须 `print(关键中间值, flush=True)`——丢了能知道跑到哪
- 结果写文件(KEY.bin / *.out / log),驱动轮询读,不靠消息通道
- 一个后台任务 = 一个文件,避免互相污染
- **后台等待期间干别的**(并行支线),不干等
- 会话可能丢:长任务可断点续跑(分块 + 落盘)

### 消息通道陷阱(实战)
- frida 早期 attach 时消息通道不稳(console.log 丢失)→ **改用文件日志**(脚本写 /data/data/.../log.txt,驱动 adb cat 读)
- 进程权限:游戏进程写不了 /data/local/tmp(owner=shell)→ 写游戏自己的 files 目录
- 输出编码:Windows GBK 终端打 ✓ 会崩 → 用 ASCII 标记(OK/★ 用 [*])

### 时长控制(实战教训)
- **后台任务不要跑太久**:wait_for_job 用短超时(60-120s),到点就查一次,别干等
- 长循环任务:每轮设上限(如 3 分钟),轮间快速反馈
- 用户在场时:每 1-2 分钟汇报一次进展,不要长时间沉默
- 大下载(web_fetch 3MB+)先确认必要再拉,注意输出会被截断
- **禁止前台长时间阻塞**(>60s 的任务一律后台);后台跑着就干别的活

### 观察进程(动手前必做)
- **先观察再操作**:启动目标后,先看 60-90s 是否稳定(pid 不变/so 加载/前台正常),确认健康才 attach/hook
- 观察项:pidof、maps 段数、topResumedActivity、进程存活时间
- 观察脚本每 10s 打印一行,落盘可查
- 操作中持续观察:每轮操作后查进程是否还活着,死了立即记录原因(崩溃日志/tombstone)
- 区分随机崩溃(模拟器转译层)与反调试击杀:对照实验(有 A 无 B)定位触发条件

### 窗口期利用(反调试场景)
- attach 后游戏可能 30 秒内自杀 → **窗口内疯狂触发**(每 2 秒点击/切场景),快速收集
- attach 时机与存活关系:早期 attach 秒死,稳定后 attach 活 30s → 先稳定再操作
- 检测是延迟的:留给你的窗口就是你的全部时间,把高频动作压进窗口
- 随机崩溃(模拟器转译层):循环启动 + 存活检查(60s)确认稳定后再继续

## 3. 突破执行(遇到墙怎么破)

### 破墙流程
1. **定位墙的类型**:反调试?性能死路?数据缺失?工具不适配?
2. **验证墙的边界**:对照实验(有 A 无 B)→ 确认触发条件
3. **找最薄的点**:换端口/改名/换时机/换工具/换数据源
4. **绕过或正面突破**:先试便宜方案,再上重方案

### 实战破墙案例(mhls)
| 墙 | 症状 | 突破 |
| --- | --- | --- |
| 反调试① | 游戏检测 frida-server → 闪退 | 换端口(31337→45678)+ 改名 + 换目录 → 稳定 |
| 反调试② | attach 后 ~30s 延迟自杀 | 30s 窗口内疯狂触发抓取;或 hook 自杀函数(exit/abort) |
| 反调试③ | frida 进程内读内存受限 | 纯 dd 外部读(零注入,游戏无感) |
| 壳自定义加载 | frida 枚举不到 so | /proc/maps 已知基址固定 → 直接按偏移 hook |
| 数学死路 | Z3 反演随机函数 38s/单字 | 确认死路,换动态;不再投入 |
| 数据缺失 | 调用者脚本不在内存 | 找设备文件(hotfix_battle/download)补数据源 |

### 反调试检测的常见面
- frida-server 进程/端口(31337 默认)→ 换端口+改名
- ptrace attach(TracerPid)→ 早期 hook 修复 /proc/self/status
- 内存特征(frida agent 字符串)→ gadget 混淆/延迟注入
- 行为特征(频繁重启/异常时序)→ 模拟正常用户节奏

## 4. 关键路径与黄金样本

- 先打通**端到端最小闭环**(1 个样本全链路),再规模化
- **黄金样本**(known-plaintext pair / 语义可推断代码)= 一切验证的基准,没有它别盲打
- 每个"确认"记录:证据来源(地址/样本)+ 验证方式
- 索引规则/字段语义这类"小规则",用黄金样本逐一验证,别猜

## 6. 常见失败模式

| 失败模式 | 症状 | 对策 |
| --- | --- | --- |
| 盲扫 | 大范围搜索全是噪声 | 先做过滤器/先想标识在哪两端 |
| 模型漂移 | 结果对不上 | 回反汇编/字节级核对 |
| 诱饵陷阱 | 路径是反调试/死循环 | 看调用链、循环终止条件 |
| 欠约束解 | SAT 但验证失败 | 约束 ≥ 未知数;多黄金样本交叉验证 |
| 消息通道丢 | 脚本输出不见 | 文件日志替代 console |
| 权限墙 | 写不了/读不了 | su 中转 / 换可写目录 / 换读取方式(dd vs frida) |
| 随机崩溃 | 启动偶发崩 | 循环重试 + 存活检查 + 稳定后再操作 |
| 单点依赖 | 卡一个外部条件 | 尽早识别,提前准备替代(如多数据源) |
