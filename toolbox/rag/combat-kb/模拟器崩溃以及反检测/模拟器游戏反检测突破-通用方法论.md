# 模拟器游戏反检测突破 — 通用方法论

> 适用范围: MuMu/雷电/夜神等 Android 模拟器上的手游 (腾讯系 TP 或其他反作弊)
> 核心原则: **观测永远安全, 修改才有风险; 先画像, 再绕过, 最后 hook**
> 案例标注: 所有具体数值以 [案例: 火影忍者] 标注, 方法本身通用

---

## 一、检测面总览 (先知道要打什么)

游戏反检测 = 四类独立检测, 必须分别突破:

| 检测面 | 检测什么 | 触发后果 | 通用应对 |
|---|---|---|---|
| **环境检测** | cpuinfo/机型/传感器/GPU/虚拟化特征 | 弹窗/降级/封号 | 伪造文件或隐藏特征 |
| **完整性校验** | 代码段指令被改 (inline hook) | 自杀 (force-crash) | 时序窗口法 (见 §三) |
| **调试检测** | ptrace 附加者 (TracerPid) | 自杀/闪退 | 大部分 TP **不检测 ptrace** (实测) |
| **行为分析** | 高频调用/异常时序/frida 特征 | 深度检查后自杀 | 伪装正常行为 |

**关键认知 (实测得出)**:
- TP 检测的是「**代码被修改**」, 不是「有人附加」→ 纯观测 (strace/eBPF/attach) 全部安全
- 检测是**事件驱动**的: 平时极安静, 出现特征才深度检查 → 有时间窗可利用
- 检测线程**只在游戏前台活跃**; 后台被 Android App Freezer 冻结 (0 syscall) → 实验必须在前台做

## 二、工具链与安全分级 (先搭观测台)

| 层级 | 工具 | 安全性 | 用途 |
|---|---|---|---|
| 应用层 | frida attach (无 hook) | ✅ 安全 | 模块枚举/读内存/符号定位 |
| 系统层 | strace -f -p (ptrace) | ✅ 安全 | syscall 路径画像 (TP 读什么) |
| 内核层 | eBPF kprobe (原生 ELF) | ✅ 安全 | 任意内核函数 + PID 过滤 + 用户/内核栈 |
| 修改层 | frida Interceptor / 代码 patch | ❌ 触发完整性校验 | 仅在时序窗口内使用 (见 §三) |
| 伪造层 | 覆盖 /system 文件 / sysctl | ⚠️ 小心交叉验证 | 环境特征伪造 |

**观测台搭建清单** (模拟器 root 环境):
```
adb connect 127.0.0.1:<端口>
adb shell su -c '...'                    # root 命令
adb forward tcp:31337 tcp:31337          # frida 通道
su -c 'nohup /data/local/tmp/x/nsv11 -D &'   # 魔改 frida server (反检测版)
strace -f -p <pid> -e trace=openat,read,newfstatat -o /data/local/tmp/x.log
```

**strace 的 -P 路径过滤** (最实用的观测手法):
```
strace -f -p <pid> -P /system/lib64/arm64/cpuinfo -e trace=read -o cpu.log
# 只观察指定文件的访问 — 确认检测循环读哪些文件、频率多少
```

## 三、★ 时序窗口法 (突破完整性校验的唯一通用手段)

### 原理
完整性校验是**周期性扫描** (不是每指令检查)。在两次扫描之间完成 hook→取数→恢复, 检测不到。

### 通用实验流程 (确定窗口大小)
```
1. hook 目标函数 (空操作) → 挂 15s → detach → 检查进程存活
2. 存活 → 挂 30s → detach → 检查      (二分法逼近窗口上界)
3. 死亡 → 用 12s 作为安全操作窗口       (留 20% 余量)
```

### 实测结论 (案例: 火影)
| 挂载时长 | 结果 |
|---|---|
| 12-15s | ✅ 存活 (多次验证) |
| 30s | ❌ 死亡 |
| 60s | ❌ 死亡 |
→ **校验周期在 15~30s 之间; 安全窗口 = 12s**

### 战术执行模板
```
attach → 装 hook (只 hook 目标, 最小化) → 立即触发活动 (input tap/swipe)
→ ≤12s 内取完数据 → 立即 detach → 进程存活
```
**局限与对策**:
- 窗口内无活动 = 无数据 → 配合 `input tap` 触发 (游戏前台)
- 高频函数 (read) 数据爆炸 → hook 里 cap 打印条数 + fd 过滤
- hook 回调里所有内存读必须 try-catch (异常刷屏会加剧检测面)
- 重试间隔: 每次实验后等 30s+ 再 attach (让校验周期错开)

## 四、环境检测绕过 — 文件伪造法 (通用流程)

### 1. 找出检测读什么
```
# strace 全路径画像 30s (前台活跃状态):
strace -f -p <pid> -e trace=openat,newfstatat,access -o paths.log
grep -E "/proc/|/sys/|/system/" paths.log | sort | uniq -c | sort -rn
```
高频读取 + 名字可疑 (cpuinfo/maps/status/版本文件) = 环境检测点。

### 2. 确认模拟器特征值
```
cat /system/lib64/arm64/cpuinfo    # 案例: implementer 0x4e (NVIDIA伪装)
cat /proc/cpuinfo                   # 真值 (伪造前记录, 交叉验证风险点)
```

### 3. 伪造 (通用步骤)
```
mount -o rw,remount /system        # overlay 通常直接可写
cp <目标文件> /data/local/tmp/<备份>   # 必须备份!
cp <伪造内容> <目标文件>
strace -P <目标文件> -e trace=read   # 验证: 检测代码读到的是伪造值
```

### 3·5. ★★ 交叉验证警示 (2026-08-15 猫和老鼠实证)
**伪造前必须先确认目标游戏是否交叉验证** — 否则伪造 = 自杀开关:

| 案例 | cpuinfo 伪造 | 结果 |
|---|---|---|
| 火影 (腾讯 TP) | 伪造高通 0x51 | ✅ 生效, TP 读伪造值不校验 |
| 猫和老鼠 (网易易盾) | 伪造高通 0x51 | ❌ **启动 1s 内故意 SIGSEGV (fault 0xdead1001, houdini+libhp15 栈)** |

- **易盾只在启动阶段校验 cpuinfo** (运行期 0 次读取); 校验方式: ARM 视图值 vs 模拟器真实值交叉对比, 不一致 → 死码崩溃
- 死码特征: `fault addr 0xdead1001` (dead + 编号, 故意触发) — tombstone 里看到这种地址 = 检测自杀
- **判断方法**: 伪造前先启动游戏确认正常; 伪造后立即重启验证; 崩 → 立即恢复备份 (cp 回原值即可)
- **安全做法**: 不确定时用 strace -P 观察是否运行期读 cpuinfo (火影读=可伪造; 易盾不读=启动校验=勿动)
**伪造要点** (案例: 高通风格):
- implementer 0x51 / part 0x804 / variant 0x0f (真机典型值)
- Features 完整长串 (含 sve sve2 bti pauth 等新特性)
- BogoMIPS 38+ / 核心数按真机 (12)
- 伪造内容存 PC 工作文件夹, 一键恢复脚本

### 4. 验证与风险
- 验证: 检测循环仍在读 (strace -P) 且内容 = 伪造值, 游戏存活
- 风险: ① 交叉验证 (对比 /proc/cpuinfo 真值 → 需同时伪造) ② 重启还原 (overlay) ③ 其他视图 (ARM 转译路径)

## 五、崩溃诊断 — 先分清真崩还是自杀

闪退 ≠ 检测自杀, 先取证再下结论:

```
1. ps -A | grep <包名>                # 是否重启 (TP 自杀常有守护重启)
2. logcat -d -b crash | tail          # Java 层崩溃
3. ls -lt /data/tombstones/ | head    # native 崩溃
4. events log: force-crash 标记?      # am_proc_died / wm_finish_activity ... force-crash
```
**判定表**:
| 特征 | 结论 |
|---|---|
| SIGSEGV pc=低地址/堆区, 单线程崩 | 兼容性 bug (模拟器 ART/转译) — 非检测 |
| force-crash + 特定 Activity 弹窗 | 检测自杀的表象 (需看根因是检测还是 bug) |
| abort/SIGABRT + 明确调用链 | 检测自杀 |
| 进程消失无 tombstone | 被 kill (需查 am_kill 原因) |

**对照实验定因果**: 无任何工具状态下操作复现? 复现 → 游戏自身问题; 不复现 → 我们的工具触发。
(案例: 火影 MSDKPolicyActivity 弹窗时 SIGSEGV, 无 hook 也偶发 → 模拟器兼容 bug, 非检测)

## 六、TP 行为画像 (通用观察清单)

检测线程通常有这些特征, 按此清单验证:
```
- [ ] 读 /proc/self/maps (低频)          → 扫 frida memfd/gum 特征
- [ ] 读 cpuinfo/机型文件 (周期)          → 环境判定
- [ ] tgkill(SIG_0) 探测线程              → 注意: Unity 启动也有此行为, 需二次对照!
- [ ] 读 /proc/self/stat + meminfo       → 性能监控 (非检测, 别误判)
- [ ] 线程名特征 (Catcher/Thread-N/无意义名)
- [ ] 只在游戏前台活跃 (后台冻结)
```
**反例警示**: 高频率 tgkill(SIG_0) 一度被误判为检测 — 二次 attach 对照证明是 Unity 线程池初始化。**任何高频行为都要二次实验排除误判**。

## 七、通用突破路线图

```
第一阶段 观测 (0 风险):
  1. 无 hook 冷启动 → 稳定基线 (1h+)
  2. strace 画像: 路径/频率/fd
  3. fd 画像: 检测循环文件清单
  4. 崩溃取证: tombstone/events 分类

第二阶段 环境绕过 (低风险):
  5. 伪造检测文件 (cpuinfo/版本等)
  6. strace -P 验证检测代码吃到伪造值

第三阶段 hook 突破 (窗口战术):
  7. 窗口大小测定 (15/30s 二分)
  8. ≤12s 窗口内 hook 目标函数取数
  9. 每次 detach 后 30s 冷却

第四阶段 纵深 (可选):
  10. ARM 侧代码 patch 验证 (转译环境特有)
  11. 内核模块隐藏 / 伪造校验结果
  12. 目标函数 hook 后的业务应用 (如 IL2CPP metadata dump)
```

## 八、易错点清单 (血泪)

1. **attach 前必重启 frida server** (否则 "timed out waiting for stop")
2. **后台冻结状态实验全无效** (先确认 topResumedActivity = 游戏)
3. **切前台操作本身可能触发崩溃** (MSDK 弹窗) — 用冷启动代替
4. **hook 回调里内存读必须 try-catch** (NULL 指针异常刷屏 = 自爆)
5. **对比实验要隔离变量** (eBPF 挂载 + monkey 切前台同时做, 误判为 hook 杀进程)
6. **用后必清理内核痕迹**: `echo > /sys/kernel/tracing/kprobe_events; echo 0 > .../tracing_on` (残留会导致下次启动闪退)
7. **eBPF PID 过滤必须 prog 内做** (perf_event_open 的 pid 参数对 kprobe 无效); pid=-1 时别把 -1 写进 imm (无符号 0xFFFFFFFF 全过滤)
8. **地址对照 maps 用数值比较** (子串 grep 匹配不到区间内地址)

## D. MuMu 进程管理陷阱（2026-09-14 实战）

### D1. MuMu 进程架构

MuMu 6.0 的 VM 进程链：
```
MuMuManager.exe → MuMuVMMHeadless.exe (QEMU) → adb.exe → n5202 (emulator)
```

每个 app 启动时**可能产生多个 PID**（LSPosed 注入会增加）：

```bash
# app 启动后
pidof com.yaodu.supplychain
# 2030 2145 2184   ← 三个 PID

# 2030 = 主进程（有 libdexjni.so，壳在这里）
# 2145/2184 = LSPosed 子进程（无 dexjni）
```

**怎么判断哪个是主进程？**
```bash
for p in $(pidof com.xxx); do
    echo "PID=$p dexjni=$(grep -c dexjni /proc/$p/maps)"
done
# 有 dexjni 的是主进程
```

### D2. kill -9 杀不掉（MuMu 坑）

```bash
# 杀进程无效？检查是否有子进程活着
adb shell "su -c 'kill -9 2030 2145 2184'"  # 全杀
pidof com.yaodu.supplychain                    # 可能还在！
```

**原因**：MuMu 的 QEMU 层会 fork 出不被 `kill -9` 控制的子进程。
必须用 `am force-stop` 而不是直接杀 PID。

```bash
# 正确的强杀方式
adb shell "su -c 'am force-stop com.yaodu.supplychain'"
pidof com.yaodu.supplychain    # → 空 = 成功
```

### D3. kill 后 app 重启（LSPosed）

如果 app 有 LSPosed 保护，`am force-stop` 会触发它自动重启：

```bash
am force-stop com.yaodu.supplychain
sleep 0.1
pidof com.yaodu.supplychain    # 立刻出现新的 PID
```

**快速锁死的方法**（冻结在原地）：

```bash
adb shell "su -c 'am force-stop com.yaodu.supplychain; \
  setenforce 0; \
  sleep 0.1; \
  PID=$(pidof com.yaodu.supplychain | cut -d\" \" -f1); \
  dd if=/proc/$PID/mem ...'  # 用 dd 直接读，不用 frida"
```

### D4. MuMu 端口映射

```bash

adb connect 127.0.0.1:7555

# MuMu 12 默认 adb 端口  
adb connect 127.0.0.1:16384

# 检查
adb devices
```

### D5. MuMu 杀模拟器（重启）

```bash

adb shell "su -c 'reboot'"

# 方法2: 强杀所有 MuMu 进程（需要等重启）
```

### D6. frida attach 时序（Android 15 app 启动快）

app 启动到 frida ready 的窗口极短：

```bash
# 铁律：先启动 app，等稳定后再 attach
adb shell "su -c 'am start -n com.yaodu.supplychain/.SplashActivity'"
```

## 五、★ 分层判据 + 堵漏斗 + 本地拟真（不用真机的部分）

> 前提：**很多检测行为可在本地用 Qiling/unidbg "拟真"摸清**（读哪些文件/syscall、接口、字符串表），再定 hook 落点；真机只做验证。

### 5.1 分层判据：看它"读环境"走哪条路 → 就在哪层堵
| 读环境方式 | 层 | 在哪堵 |
|---|---|---|
| libc 函数(open/prctl/popen) | libc | hook libc 导出 |
| libc `syscall()` 包装 | libc | hook `syscall` |
| **内联 `svc #0`** | raw svc | **libc 钩不到** → patch svc / seccomp |
| **自带 syscall 引擎**(`xxx_syscall(nr,...)`) | raw svc | **hook 那个引擎** |
| Java API(getPackageName/Settings.Secure) | Java | 改方法返回 |

**判据**：扫 `.text` 数**内联 `svc` 条数**（0=全走 libc；>0=有绕过）；看是否有**自定义 syscall 引擎导出**。

### 5.2 堵漏斗 > 堵点
检测点可能列不全（漏一个即上报）。**找"汇总通道"堵它**：
- native 命令通道（`ioctl`/`gp*ioctl`）、Java 上报回调 = **漏斗**。
- 例：某 ACE 的 Java `initialize()` 返回非0 → 抛异常 → 上报 → **hook 返回 0**，一行顶 native 一堆检测。

### 5.3 本地拟真能拿到什么（无真机）
- **Qiling**：init/JNI_OnLoad 行为（读哪些 `/proc/*`、syscall 路径）；auto-map 未映射页让它跑到底。
- **unidbg**：真 JNIEnv 下**调 native 方法**；`hook RegisterNatives` 捕获接口；**枚举取串函数**得全字符串表；触发到自退点。
- → 定出"**检测点清单 + hook 落点**"，真机只做验证。
