# x86_64 模拟器 Frida 注入通用方法论

> 适用场景：Android x86_64 模拟器上对任意 App（含 ARM/ARM64 native 库）进行 Frida 动态分析。
> 验证案例：快手 `com.smile.gifmaker` v14.4.30，MuMu Player 12，Kitsune Mask 27002。

## 一、x86_64 模拟器 SO 加载原理

> 核心问题：在 x86_64 模拟器上运行 ARM 应用，native 库走 NativeBridge 翻译路径而非标准 dlopen。

```
Java System.loadLibrary("foo")
  ↓
do_dlopen()                    ← linker 入口
  ↓
find_library()                 ← 读 ELF header，判断 SO 的 CPU 架构
  ↓
OpenNativeLibrary()            ← 🎯 分叉点
  ├── SO 是 x86_64
  │     ↓
  │   dlopen() @ libdl.so      ← 标准 ELF 加载（可直接 Hook）
  │
  └── SO 是 ARM/ARM64
        ↓
      NativeBridgeLoadLibrary() @ libnativebridge.so
        ↓
      libhoudini.so             ← ARM→x86 二进制翻译引擎
        ↓
      loadLibrary() @ NativeBridgeItf  → 实际映射 SO
```

### NB 核心模块（所有 x86_64 设备通用）

| 模块 | 作用 | Hook 方式 |
|------|------|-----------|
| `libnativebridge.so` | 桥接层，提供 `NativeBridgeLoadLibrary(Ext)` | 直接 Hook 导出函数 |
| `libhoudini.so` | ARM→x86 翻译引擎，内含 `NativeBridgeItf` 结构体 | 搜索符号→读指针→Hook |
| `libnb.so` | NativeBridge 助手 | — |
| `libtcb.so` | 线程控制块，ARM so 加载后动态载入 | Hook dlopen 捕获 |

## 二、注入模式选择

### 2.1 Spawn 模式（`frida -f`）

```
流程: Frida fork 进程 → 注入 agent → 脚本 Hook → resume
适用: 无强检测的普通 App
风险: 强检测 App 在初始化阶段有陷阱（如快手 base.odex 匿名内存 SIGSEGV handler）
```

### 2.2 Attach 模式（`frida -p`/`-n`）

```
流程: App 正常启动 → 初始化完成 → Frida attach → Hook
适用: 有反调试/spawn 检测的 App
原理: 多数 App 的检测只在启动阶段跑一次，之后不再检查
启动: monkey -p <pkg> -c android.intent.category.LAUNCHER 1
```

### 2.3 选择流程图

```
目标 App
  ├─ spawn 不崩 → 直接用 spawn（Hook 覆盖全生命周期）
  └─ spawn 崩   → 切 attach 模式
       ├─ attach 不崩 → ✅ 走 attach
       └─ attach 也崩 → 走 Zygisk（需编译 .so 模块）
```

## 三、系统库 Hook 通用策略

### 3.1 三层 Hook 矩阵

| 层 | 目标 | 抓什么 | 典型模块 |
|----|------|--------|----------|
| **Native 系统库** | libc, libdl, libssl | 文件/进程/网络操作 | `fopen`, `dlopen`, `SSL_write` |
| **Java 系统类** | java.security, javax.crypto | 加密/签名算法 | `MessageDigest`, `Cipher`, `Mac` |
| **Java 网络类** | java.net, okhttp | HTTP 请求 | `URL.$init`, `OkHttpClient` |

### 3.2 Native 层 Hook 模板

```javascript
// 通用：Hook 任意 so 的导出函数
function hookExport(modName, funcName, onEnterFn) {
    var m = Process.findModuleByName(modName);
    if (!m) return;
    m.enumerateExports().forEach(function(e) {
        if (e.name === funcName)
            Interceptor.attach(e.address, { onEnter: onEnterFn });
    });
}

// 文件访问
hookExport("libc.so", "fopen", function(args) {
    var p = args[0].readCString();
    if (p) console.log("[fopen] " + p);
});

// SO 加载
hookExport("libdl.so", "android_dlopen_ext", function(args) {
    console.log("[dlopen] " + args[0].readCString());
});

// NativeBridge ARM SO 加载
hookExport("libnativebridge.so", "NativeBridgeLoadLibraryExt", function(args) {
    console.log("[NB] " + (args[1] ? args[1].readCString() : "?"));
});
```

### 3.3 Java 层 Hook 模板

```javascript
Java.perform(function() {
    // 加密算法
    var MD = Java.use("java.security.MessageDigest");
    MD.getInstance.overload('java.lang.String').implementation = function(algo) {
        console.log("[MD] " + algo);
        return this.getInstance(algo);
    };

    var Cipher = Java.use("javax.crypto.Cipher");
    Cipher.getInstance.overload('java.lang.String').implementation = function(algo) {
        console.log("[Cipher] " + algo);
        return this.getInstance(algo);
    };

    // URL 请求
    var URL = Java.use("java.net.URL");
    URL.$init.overload('java.lang.String').implementation = function(url) {
        console.log("[URL] " + url);
        return this.$init(url);
    };
});
```

## 四、NativeBridgeItf 深度 Hook

> 原理：`libhoudini.so` 导出 `NativeBridgeItf` 结构体，内含 14 个函数指针。直接读结构体偏移 Hook，可捕获所有 ARM64 so 的加载。

```c
// NativeBridgeItf 结构体 (x86_64, version=6)
struct NativeBridgeCallbacks {
    uint32_t version;                // +0x00: 版本号
    uint32_t padding;                // +0x04: 对齐
    void* initialize;                // +0x08
    void* loadLibrary;               // +0x10 ← 🔴 核心 Hook：ARM SO 加载
    void* getTrampoline;             // +0x18
    void* isSupported;               // +0x20
    void* getAppEnv;                 // +0x28
    void* isCompatibleWith;          // +0x30
    void* getSignalHandler;          // +0x38
    void* unloadLibrary;             // +0x40
    void* getError;                  // +0x48
    void* isPathSupported;           // +0x50
    void* initAnonymousNamespace;    // +0x58
    void* createNamespace;           // +0x60
    void* linkNamespaces;            // +0x68
};
```

### Hook 方式

```javascript
// 方式 A: 读结构体 → Hook 函数指针（最底层，能捕获所有 ARM SO）
var houdini = Process.findModuleByName("libhoudini.so");
houdini.enumerateExports().forEach(function(e) {
    if (e.name === "NativeBridgeItf") {
        var loadLib = e.address.add(0x10).readPointer();
        Interceptor.attach(loadLib, {
            onEnter: function(args) {
                console.log("[NB::loadLibrary] " + args[1].readCString());
            }
        });
    }
});

// 方式 B: Hook libnativebridge.so 导出（更方便）
hookExport("libnativebridge.so", "NativeBridgeLoadLibraryExt", function(args) {
    console.log("[NB-ext] " + args[1].readCString());
});
```

### 5.1 SSL 明文抓取

| Hook 点 | 模块 | 抓取内容 |
|----------|------|----------|

### 5.2 与 Burp 联动

```
Frida Hook SSL_write/read → 拿到明文

  ↓
Python 端解析 HTTP → 保存 .http 文件
  ↓

```

## 六、Root/环境检测验证

### 6.1 通用检测维度

| 检测方式 | Hook 目标 | 判断标准 |
|----------|-----------|----------|
| 文件检测 | `File.exists` / `fopen` / `access` | 是否传入 su/magisk 路径 |
| 命令检测 | `Runtime.exec` / `ProcessBuilder.start` | 是否执行 `which su` 等 |
| 包名检测 | `PackageManager.getPackageInfo` | 是否查询 magisk/xposed 包名 |
| 属性检测 | `SystemProperties.get` | `ro.debuggable` / `ro.build.tags` 值 |
| maps 检测 | `BufferedReader(FileReader)` | 是否读取 `/proc/self/maps` |

### 6.2 判定逻辑

```
全部维度 0 次调用 → ✅ 未检测 / 伪装完全生效
任意维度有调用   → ⚠️ 需要针对性 Hook 拦截
spawn 崩         → 初始化阶段检测，切 attach
```

## 七、加密参数逆向流程

### 7.1 定位步骤

```
1. Hook MessageDigest.getInstance → 确认算法（MD5/SHA-1/SHA-256）
2. Hook MessageDigest.digest      → dump 输入原文（HEX）
3. Hook Cipher.getInstance        → 确认对称加密算法（AES/DES）
4. Hook Base64.encodeToString     → 确认编码方式
5. Hook URL.$init                 → 抓完整请求 URL + 参数
```

### 7.2 常见加密模式

```
模式 A: 无加密
  URL?param1=v1&param2=v2&sign=MD5(params+key)

模式 B: 对称加密
  body = AES_CBC(JSON, key, iv)
  body = Base64(ciphertext)
  sign = SHA1(JSON)
  URL?bodyMd5=MD5(JSON)&sign=XXX

模式 C: 非对称加密
  body = RSA_PublicKey_Encrypt(JSON)
  sign = SHA256(PrivateKey_Sign(JSON))
```

### 7.3 快手案例：模式 B

```
1. 原始 JSON body → MD5 → bodyMd5 (URL 参数)
2. 原始 JSON body → AES/CBC/PKCS5Padding 加密
3. 密文 → Base64.encode → 最终 body 字段
4. SHA-1(body) → Base64.encode → sign（27 字符）
```

## 十、x86_64 syscall Hook（兜底方案）

> 适用场景：App 绕过 libc 直接用 `syscall` 指令调系统调用，libc Hook 抓不到。

### 10.1 ARM vs x86_64 对比

| | ARM64 | x86_64 |
|---|-------|--------|
| 指令 | `SVC #0` | `syscall` |
| 调用号寄存器 | `x8` | `rax` |
| open | `SVC #0, x8=0x38` | `syscall, rax=2` |
| openat | `SVC #0, x8=0x38` | `syscall, rax=257` |
| access | `SVC #0, x8=0x30` | `syscall, rax=21` |
| stat | `SVC #0, x8=0x18` | `syscall, rax=4` |
| faccessat | `SVC #0, x8=0x30` | `syscall, rax=269` |

### 10.2 x86_64 完整 Hook 模板

```javascript
// x86_64 syscall hook
// Hook 点: libc.so 的 __syscall / syscall 函数
var libc = Process.findModuleByName("libc.so");
libc.enumerateExports().forEach(function(e) {
    if (e.name !== "__syscall" && e.name !== "syscall") return;

    Interceptor.attach(e.address, {
        onEnter: function(args) {
            var nr = args[0].toInt32(); // x86_64: rax=syscall number
            var blocked = false;
            switch (nr) {
                case 2:   // open
                case 257: // openat
                    var path = args[1].readCString();
                    if (path && isBlockedPath(path)) { blocked = true; }
                    console.log("[syscall open] " + path);
                    break;
                case 21:  // access
                case 269: // faccessat
                    var path = args[1].readCString();
                    if (path && isBlockedPath(path)) { blocked = true; }
                    console.log("[syscall access] " + path);
                    break;
                case 4:   // stat
                case 6:   // lstat
                    var path = args[1].readCString();
                    if (path && isBlockedPath(path)) { blocked = true; }
                    console.log("[syscall stat] " + path);
                    break;
            }
            if (blocked) {
                // 让 syscall 返回 -1 (ENOENT)
                this.block = true;
                args[1] = ptr(0); // 清空路径指针 — 让调用失败
            }
        },
        onLeave: function(ret) {
            if (this.block) ret.replace(ptr(-1));
        }
    });
    console.log("[syscall] hooked");
});
```

### 10.3 判断是否需要 syscall Hook

```
验证方法:
  Hook libc.fopen → 如果有 fopen 调用被记录，说明走标准路径
  Hook syscall     → 比对 fopen 和 syscall open 的调用次数
  如果 syscall 次数 > fopen 次数 → App 绕过了 libc
```

### 10.4 快手案例结论

```
libc.fopen 调用存在 & 正常触发 → 走标准路径
libcrypto.so MD5/SHA 零调用     → 加密在 Java 层
syscall hook 不需要             → 快手 attach 模式已全覆盖
```
