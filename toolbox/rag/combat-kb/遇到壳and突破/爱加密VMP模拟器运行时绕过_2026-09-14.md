# 爱加密（Ijiami）VMP 运行时绕过 — 模拟器篇

> 2026-09-14 实战验证 | 目标: com.yaodu.supplychain（银行供应链金融）
> 环境: MuMu 6.0 / Android 15 / x86_64 + Houdini ARM 转译

---

## 一、一句话总结

**爱加密在 x86_64 模拟器上的 VMP 可以绕过（不是破解）。**
壳把真 dex 解密在匿名 RW- 内存里且自己不锁，用 `dd if=/proc/PID/mem` 直接拉出来。
不拆壳、不逆壳算法、不过反调试——纯内存取证。

## 二、爱加密特征识别

### 2.1 必中特征

| 特征 | 位置 | 说明 |
|---|---|---|
| `libDexHelper-x86.so` | `lib/arm64/` | **x86_64 原生 SO**（非 ARM 转译） |
| `libdexjni.so` | `lib/arm64/` | ARM64 解密引擎（Houdini 转译跑） |
| `assets/*.dat` | 资产目录 | RC4 加密的数据文件 |
| `assets/info.y` | 资产目录 | 百度地图配置（壳附带） |
| base.apk 几 MB | APK | 壳本体小，真 dex 加密在内 |

### 2.2 运行时特征

```bash
# 1. maps 里 libDexHelper-x86.so 是 rwxp（自修改代码）
grep DexHelper /proc/PID/maps
# 7bdb6f2a6000-7bdb6f3c5000 rwxp ... libDexHelper-x86.so

# 2. 壳熵值变化（磁盘加密 vs 内存解密）
# 磁盘: 熵 ~4.3（加密态）
# 内存: 熵 ~6.4（解密态）

# 3. 进程有 ARM64 SO 在 0x4000xxxx 区间
grep libdexjni /proc/PID/maps
# 400020e00000-400020r--p ... libdexjni.so
```

## 三、核心突破点：壳不防内存读

爱加密的反调试集中在：
- `/proc/PID/status` 读 TracerPid ← frida 注入后 `__system_property_get` hook 可骗
- `/proc/PID/maps` 检查 ← 但**不检查 `/proc/PID/mem`**
- `ptrace(PTRACE_TRACEME)` ← 双进程保护

**致命漏洞**：壳解密后的 dex 放在匿名 RW- 内存，自己没锁、没抹、没加密——全裸。

## 四、五步绕过流程

### Step 0: 前提条件

```bash
# 1. root + 关 SELinux
su -c 'setenforce 0; getenforce'  # → Permissive

# 2. 装 frida-server（nosuke 版，用 -D 模式）
adb forward tcp:31337 tcp:31337

# 3. 装 Python 3 + frida 库
```

### Step 1: 扫内存找大 dex（frida）

核心脚本 `scan_bigdex.py`：

```javascript
var ranges = Process.enumerateRanges('r--').concat(
              Process.enumerateRanges('rw-')).concat(
                Process.enumerateRanges('r-x'));

// 注意：只找 classes > 500 的 dex（排除框架 jar 的小 dex）
pats.forEach(function(pat) {
    Memory.scanSync(r.base, r.size, pat).forEach(function(x) {
        var h = x.address.readByteArray(0x70);  // 只读头
        var cls = new DataView(h).getUint32(0x60, true);   // class_defs_size
        var fsz = new DataView(h).getUint32(0x20, true);  // file_size
        if (cls > 500 && fsz < 60000000) {
            // → ROADMAP: 这就是目标 dex 的地址
        }
    });
});
```

**过滤规则**（经验值）：
| 条件 | 值 | 说明 |
|---|---|---|
| `classes > 500` | 排除内置 jar 小 dex | framework.jar ~8800 类但那是系统不是 app |
| `file_size < 60MB` | 排除异常值 | 壳伪造的 vdex 有时写超大 |
| `file == "anon"` | 只找匿名内存 | 框架 jar 的 dex 有文件路径 |
| `strings > 10000` | 排除 stub | 爱加密 stub = 354 strings |

### Step 2: Python 算 skip（避免 mksh 32 位截断）

```python
addr = 0x7bdb7566e000    # frida 扫到的地址
size = 9025140            # file_size
skip = addr // 4096       # dd bs=4096 时的块数
count = size // 4096 + 1
print(f'skip={skip} count={count}')
```

**永远不要在 shell 里 `$((0x7bdb71558000/4096))`**——mksh 截断到 32 位。

### Step 3: dd 从 /proc/PID/mem 拉取

```bash
su -c 'PID=$(pidof com.yaodu.supplychain | cut -d" " -f1); \
  dd if=/proc/$PID/mem of=/data/local/tmp/dex.bin \
  bs=4096 skip=<skip> count=<count>'

# 验证头
head -c 8 /data/local/tmp/dex.bin | xxd
# → 00000000: 6465 780a 3033 3500  就是 "dex\n035"
```

### Step 4: 验证 dex 完整性

```bash
python -c "
import struct
d = open('dex.bin','rb').read()
def u32(o): return struct.unpack('<I', d[o:o+4])[0]
print(f'file_size={u32(0x20)} strings={u32(0x38)} methods={u32(0x58)} classes={u32(0x60)}')
"
```

真 app dex 的典型特征：
- `methods` > 10000（stub 只有 200+）
- `classes` = app 真实类数
- `strings` > 10000

### Step 5: jadx 打开

```
jadx-gui classes.dex classes2.dex
```

## 五、备用方案：frida hook 抓 OpenMemory

如果 dd 来不及（窗口期极短），可以 hook `art::DexFile::OpenMemory` 在壳加载 dex 时直接抓：

```javascript
function hookDexLoad() {
    ['libdexfile.so', 'libart.so'].forEach(function(modname) {
        var mod = Process.findModuleByName(modname);
        if (!mod) return;
        mod.enumerateExports().forEach(function(s) {
            if (s.name.indexOf('OpenMemory') >= 0 || s.name.indexOf('OpenCommon') >= 0) {
                Interceptor.attach(s.address, {
                    onEnter: function(args) {
                        var base = args[0];
                        var size = args[1].toInt32();
                        if (size > 1000 && size < 60000000) {
                            try {
                                var magic = base.readByteArray(8);
                                if (magic[0] === 0x64 && magic[1] === 0x65 && magic[2] === 0x78) {
                                    var buf = base.readByteArray(size);
                                    var fn = '/data/local/tmp/dex_' + size + '.dex';
                                    var f = new File(fn, 'wb'); f.write(buf); f.close();
                                    console.log('SAVED ' + fn);
                                }
                            } catch(e) {}
                        }
                    }
                });
            }
        });
    });
}
```

**注意**：hook 必须在 app 启动**前**装好。但 `am start -D` 不冻结 native init，spawn 又失败。
所以 hook OpenMemory 方案在模拟器上**不太可行**（窗口太短），优先用 Step 1-4 的内存扫描。

## 六、两种 dex 形态

爱加密会在进程内存产生两种 dex：

| 形态 | 大小 | 类数 | 内容 | 提取方法 |
|---|---|---|---|---|
| **Stub dex** | ~15MB | 9 类 | 壳桩，方法体全是假 | 从 vdex 解 |
| **Real dex 1** | ~8.6MB | ~6900 类 | 第三方库 + 框架 | 匿名 RW- 区 dd |
| **Real dex 2** | ~5.6MB | ~5600 类 | **APP 真身** | 匿名 RW- 区 dd |

Real dex 2 是真正的目标——类名被 ProGuard 混淆（A, B, C...），但包结构完整。

## 七、常见坑

| 坑 | 原因 | 解决 |
|---|---|---|
| `readByteArray` Permission denied | SELinux + process_vm 双拦 | `setenforce 0` + dd |
| `$((addr/4096))` 算错 | mksh 32 位算术 | Python 算 |
| `Memory.scanSync` 找不到 app dex | 壳还没解密 / 搜错 magic | 等 5-10s 再扫 |
| 扫到 50 个 dex 大部分是框架 jar | 过滤条件太宽 | `classes>500` + `file==anon` |
| `findModuleByName` 找不到 ARM SO | Houdini 转译 SO 不在 x86 模块表 | 查 maps 地址 |
| 找到的 dex 只有 9 类 | 那是 stub 不是真身 | 继续扫匿名区 |
| 进程有 3 个 PID | LSPosed 注入了 2 个子进程 | 找主进程（有 dexjni 的） |
