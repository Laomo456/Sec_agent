# 移动渗透 — App 后端 API 测试 通用方法论

> 适用范围: 自研 App（原生/H5 混合）的后端 HTTP API、多租户智慧校园/企业办公类平台
> 定位区分: **本技能打"App 的后端"，不是"App 本身"**
> — 客户端逆向（脱壳/frida/so）→ `know-base-android-re` / `know-base-native-re`
> — 前端 H5 里的加密与签名还原 → `know-base-web-re`
> — 本技能负责: 从客户端提取资产面 → 测后端鉴权与越权 → 严格定性数据泄漏
> 核心原则: **先拿到"能打通的身份"（哪怕零凭据），再按鉴权模型成族测试；规模结论必须用边界算术验证**

---

## 一、面总览（移动渗透的四个层面）

| 层面 | 打什么 | 产出 | 常见缺陷 |
|---|---|---|---|
| **① 资产面提取** | 从客户端拿到全部端点与参数 | 端点清单 | 接口文档泄漏、注释残留、调试端点 |
| **② 身份获取** | 免凭据/弱凭据会话 | 可用 token | 游客登录、跳过登录、测试账号 |
| **③ 鉴权模型测绘** | 服务端到底认什么 | 鉴权规则 | 客户端可自报身份、参数覆盖 token |
| **④ 越权与泄漏** | 横向/纵向/跨租户取数据 | 数据成果 | 缺授权判定、分页被忽略、字段过度返回 |

**关键认知**：移动端 App 的安全边界**几乎全在后端**。客户端能反编译、能 hook，这是既定的；**所以"客户端做了什么防护"基本没有意义，唯一有意义的问题是——服务端认不认。**

## 二、资产面提取（第一步，决定后面全部工作量）

### 2.1 从 APK 提取端点（本 case 的核心动作）

**APK 里的 H5 资源 + JS 里藏着完整端点清单。** 顺序：

```bash
# 1) 解包（有壳先脱壳 → 见 know-base-android-re）
apktool d app.apk -o unpacked/          # 或直接 unzip 拿 assets/
# 2) H5 资源通常在 assets/www 或 assets/dist
find unpacked/assets -name '*.js' -o -name '*.json' -o -name '*.html'
# 3) 用 rg 批量抽端点（比逐个读快几十倍）
rg -o '"[A-Za-z0-9_/-]+\.(?:do|htm|htm5|action|json)"' assets/www -N | sort -u
```

**更高阶：抽「常量名 → 路径」映射。** 前端习惯写成一张表：
```js
t.GET_USER_LIST = "user/queryUserList.htm";
t.SAVE_LEAVE    = "leave/saveLeave.do";
```
正则抽这两个字段，就能同时拿到**端点**和**它的业务语义**（这比只有路径值钱得多）：
```python
re.findall(r'(\w+)\s*=\s*"([A-Za-z0-9_/.-]+\.(?:do|htm|action))"', js)
```

`[案例]` 从一份 6.6 MB 的 dex + H5 资源里抽出 **826 个端点 / 701 条常量映射**，比全靠盲扫省了几个小时。

### 2.2 前缀即路由分组

端点常按前缀分组，**分组往往对应鉴权强度不同的链路**：
```
interface/rest/http/     ← "对外 REST"，最常见于泄漏
baseCampus/  oaCampus/  jwCampus/  newsCampus/  infoCampus/
managerCampus/  friendCampus/
```
**先按前缀分组再扫**：同一个端点在不同前缀下鉴权可能不同。`[案例]` 826 端点 × 8 前缀扫下来，**能出数据的集中在 1 个前缀**，其余 7 个基本 404 —— 这个分布本身就是情报。

### 2.3 别漏「配置下发」接口

App 启动时常请求一个配置接口，**返回里可能有内网地址、OSS 桶、调试开关**。
`[案例]` 从配置与落盘数据里拿到内网服务地址、OSS 桶域名、`oauth` 配置。

## 三、身份获取（零凭据优先）

**目标是拿到一个"能打通"的 token，不是拿到某个人的账号。** 按优先级找：

| 途径 | 形态 | 价值 |
|---|---|---|
| **游客/匿名登录** | `login/gusetLogin.do`、`guestLogin`、`skipLogin` | ★★★ 零凭据，最干净 |
| 自注册 | `register`、`parent/setBindRelation` | ★★ 自己注册的账号**不计分**，但可测逻辑 |
| 试用/演示租户 | 演示站点、`demo` 账号 | ★★ 常与生产同库 |
| 硬编码凭据 | 前端 JS / 反编译里的测试账号 | ★ 需判断是否真有效 |

`[案例]` 游客登录只要一个 `uuId`（客户端自造），返回即得 token；该会话的 `parentUserName="guest"`、`loginTimes=0`。

**游客 token 的价值判定**：
- 能读**公开字典**（校区名、院系列表）→ 正常设计
- 能读**他人业务数据** → **这就是漏洞本身**

> **注意计分口径**：游客/自注册账号**不能算"拿到账号权限"**（那不是"拿到别人的"）。但**用游客身份读到他人数据**是实打实的数据越权。

## 四、鉴权模型测绘（决定测试怎么成族）

**先搞清服务端认什么，再设计用例。** 四个必测点：

### 4.1 身份取自 token 还是取自请求参数？

**做法**：在请求体里塞身份字段，看是否被采信。
```
param.userId   = 1 / -1 / 他人ID
param.userName = "admin" / 不存在的值
param.realName = "管理员"
param.schoolId = 1
URL ?userId=1
```
**判据**：
- 响应**完全不变** ⇒ 参数被忽略，身份取自 token ⇒ **防护正确**
- 响应**变了**（返回了指定的他人数据）⇒ **越权，且是最严重的一类**

`[案例]` 塞 `userId=1`/`userName=admin` 全部返回同一份数据 ⇒ 参数不被采信（防护有效）；另一处 `schoolId` 传 12 种取值响应**逐字节相同** ⇒ 租户由 token 决定（防护有效）。

### 4.2 无 token / 错 token 的行为

```
无 token 头          → {"msg":"invalid token","msgState":0}
乱填 token           → ?
别人的 token         → ?
```
`[案例]` 实测是"**任意 token 皆可，但无 token 不行**" —— 说明只做了"存在性校验"没做"有效性校验"，**这个结论本身就值得单列**（它意味着 token 一旦泄漏无法吊销）。

### 4.3 token 的生命周期与绑定

- 是否绑定设备/UA/IP？（换设备用同一 token 能否继续）
- 过期时间？能否续期？
- 多端并发是否互踢？

### 4.4 把结论画成表

| 请求 | 字段取值 | 服务端是否采信 | 结论 |
|---|---|---|---|
| 带游客 token | userId=1 | 否 | 身份取自 token ✅ |
| 带游客 token | schoolId=9999 | 否 | 租户取自 token ✅ |
| 无 token | — | — | 拒绝（仅判存在性）⚠ |

**这张表决定了后面的越权测试族该怎么设计。**

## 五、越权与泄漏测试族

### 5.1 四个族

| 族 | 测什么 | 变体做法 |
|---|---|---|
| **水平越权（IDOR）** | 用 A 的身份读 B 的数据 | 替换 `userId`/`id`/`orderId` 为他人值；遍历 ID |
| **纵向越权** | 低权身份调高权接口 | 游客/普通用户调管理员端点（`managerCampus/` 前缀） |
| **跨租户** | 改租户标识读他校/他公司数据 | 换 `schoolId`/`tenantId`/`orgId` |
| **无授权** | 接口根本没做权限判定 | 直接调，看是否返回全量 |

### 5.2 分页被忽略 —— 最容易被漏的高危

**现象**：`pageSize` 传 2 / 10 / 50 / 200 / 1000 / 5000，**返回条数完全不变**，且响应里没有 `total`/`totalPages`。

**含义**：服务端不做分页，**单响应直接吐出全表**。这是"最省事"的泄漏 —— 一次请求拿全量。

`[案例]` 某接口单请求返回 **46,785 条**用户目录。

### 5.3 分页参数名反推（别猜）

**响应里会回显它自己用的字段名**，照着用它：
```json
{"offset":1, "limit":10, "totalCount":52205, "totalPages":5221, "list":[...]}
```
⇒ 正解是 `offset` + `limit`，**不是** `page`。

`[案例]` 我先用 `page` 传了 13 种类型（数组/对象/null/负数…）全部无差异，误判"该接口不分页"；看到响应里有 `offset`/`limit` 才反应过来是**参数名用错了**。

### 5.4 写接口的识别（必须做，且必须停手）

**有些"查询"名义的端点其实是写操作。** 识别标记：
```json
{"REST_AFFECTED_ROW_NUM": n}   ← UPDATE/DELETE 影响行数
{"REST_AUTO_INSERT_KEY": id}   ← INSERT 自增主键
```
一旦响应出现这类字段，**说明刚才那次请求改了数据**。

> **安全纪律**：批量扫描时**先把已知写接口加黑名单**；发现新的写接口后**立即记录下来并停止再触**。用通用 payload 全量扫是会造成副作用的——`[案例]` 我就是这么误触了 5 个写接口，行数还没记，只能建议甲方自行核查。
>
> **报告里必须如实声明自己的操作足迹**，不能只写"发现写接口可达"而不提"我触了"。

## 六、签名机制的三个必测点

移动 API 常见形态：`sign = md5("&".join(sorted(k+"="+v for k in fields)))`。

**三点必测（都是高频设计缺陷）：**

### 6.1 密钥是不是由客户端提交？

把 `appKey` 换成 `"ZZZZZZ"` / `""` / 任意值，**签名自洽** → 若仍 200：
```
⇒ 服务端用【客户端提交的 appKey】去验签 ⇒ 签名零保护，可完全离线构造请求
```
**反证**：不带 `appKey` 字段 → 500 鉴权失败 ⇒ 说明它确实在用它验签，只是取了不该取的值。

### 6.2 签名覆盖整个 body 吗？

在 body 里**追加一个额外字段**，签名不动：
- 仍 200 ⇒ **只覆盖固定字段，其余可自由注入**
- 500 ⇒ 覆盖完整（正常）

### 6.3 有没有防重放？

| 测试 | 做法 |
|---|---|
| 重放 | 同一条已签名请求**连发 N 次** |
| 时间戳 | `time` 传 `0` / `1` / `±1年` / `-30天` |

全部成功 ⇒ **无 nonce 且时间戳完全不校验** ⇒ 拦到的任何一条请求都能离线无限重放（对写操作接口可造成重复提交）。

> **结论要带边界**：签名失效 ≠ 越权。身份通常仍取自 token。**把"能伪造请求"和"能拿到别人数据"分开讲**，否则报告会显得不专业。

## 七、网关层测试（REST 网关常是独立一跳）

`interface/rest/http/` 这类前缀往往是**转发网关**，值得单独测：

| 测什么 | payload |
|---|---|
| 路径穿越 | `../`、`../../`、`..%2f`、`%2e%2e/`、`//` |
| 绝对 URL（SSRF） | `http://127.0.0.1:PORT/...` |
| 文件读取 | `../../../etc/passwd`（看是否返回 nginx/tomcat 的 404 模板，可判层级） |

`[案例]` 8 种变体全部 404/400 ⇒ 网关不做任意外发（**防护有效，这是个有价值的负面结论**）。

## 八、数据泄漏的严格定性（最容易翻车的地方）

**"拿到数据"和"证明数据是什么"是两件事。** 报 `critical` 之前必须把字段性质钉死。

### 8.1 字段性质验证：以身份证号为例

**"18 位数字"是极弱的判据** —— 订单号、序列号、内部 ID 都可能是 18 位。**必须跑完整校验：**

| 判据 | 内容 | 随机数字通过率 |
|---|---|---|
| ① 结构 | 18 位（17 数字 + 末位数字/X） | — |
| ② 出生日期 | 第 7-14 位是合法 `YYYYMMDD`（月 01-12，日按月份与闰年） | ≈ 3% |
| ③ **校验位** | 第 18 位 = `ISO 7064:1983 MOD 11-2` 加权校验码 | **9.1%（1/11）** |
| ④ 行政区划 | 前 6 位是真实省级代码 | — |
| ⑤ **交叉印证** | 第 17 位编码性别，与响应里**独立的 `sex` 字段**比对 | — |

```python
W  = [7,9,10,5,8,4,2,1,6,3,7,9,10,5,8,4,2]
CK = "10X98765432"
ok = (CK[sum(int(s[i]) * W[i] for i in range(17)) % 11] == s[17].upper())
```

**①②③ 联合通过率 < 1/1000，再加 ⑤ 交叉印证，才叫"确认"。**

`[案例]` 85 个样本 ①②③ **100% 通过**，且 ⑤ **28/28 吻合**，省级分布以本地为主（符合高校师生来源）⇒ 确认。

> **反面教训**：我先只做了 ①，就在报告里写"居民身份证号"。**判据不足就下结论，评审一问就塌。**

### 8.2 其他字段的定性

| 字段 | 不要怎么做 | 要怎么做 |
|---|---|---|
| 手机号 | 只看长度 11 | 正则 `^1[3-9]\d{9}$` + 抽样看是否落在号段规律内 |
| 邮箱 | 只看有 `@` | 提取域名，看是否是企业域（企业域 = 真员工） |
| 密码 | **看到 `password` 字段就报凭据泄露** | **先看值**！`[案例]` 该字段恒为空串 ⇒ **不是凭据泄露，必须排除** |
| 权限值 | 只列 `role` 值 | 用不同 role 的账号横向对比可访问面 |

### 8.3 规模必须用边界算术验证

**不要直接引用 `totalCount`。** 做法：二分或线性找**最后一个有数据的页**，用边界反算总数。

`[案例]`：
```
offset=5219 → 10 条
offset=5220 → 10 条
offset=5221 →  5 条   ← 最后一页
offset=5222 →  0 条
5220 × 10 + 5 = 52,205  ← 与 totalCount 精确吻合 ✅
```
**只有算术吻合，才敢写"全量可导出"。**

## 九、数据成果的形态与处理纪律

### 9.1 证据以"统计 + 格式"为主

**报告不需要数据本体。** 能证明问题的东西是：
- 字段清单（30 个字段名）
- 判据通过率（校验位 85/85）
- 规模与边界算术
- 交叉印证（性别位 vs `sex` 字段）
- 脱敏样例（`110108********3714`）

### 9.2 若确需抽样落盘

**默认只做抽样，且必须带处理声明。** 文件头写清四件事：

```
# ★ 含真实个人信息（居民身份证号 / 手机号 / 邮箱）
#   用途: 仅限向校方核实漏洞影响范围
#   禁止: 转发 / 上传在线系统 / 纳入普通报告附件
#   存储: 仅限本机，不得进入版本库、云盘、邮件
#   销毁: 核实完成后 7 日内删除
```

**同时**：
- 目录名**不要**带 `pii`/`leak`（用中性的 `evidence/`）
- 控制台**只输出元数据**（`[案例]` 我为了演示格式把前 3 条打到了控制台，那 3 条就进了工具日志 —— 本可以只显示表头）
- 自己写的脚本**注释里也不能粘真实值**（`[案例]` 我在注释里粘过真实证件号，是审计时自己发现的）

## 十、踩坑清单（都是实测踩过的）

| 坑 | 现象 | 真因 | 正确做法 |
|---|---|---|---|
| **响应截断** | 大批端点被判"非 JSON" | `read(300KB)` 截断 → `json.loads` 失败 → 被丢弃 | 上限给足（8 MB）；**"响应越大越可能是泄漏"**，要当优先目标而不是丢 |
| **响应键名** | 有数据却解析出 0 条 | 键名不是 `list`（是 `userList`/`rows`/`records`） | **先打印顶层键名** |
| **参数名** | 传了没反应 | 参数名不对（`offset` 而非 `page`） | 看响应回显的字段名反推 |
| **编码** | 中文变 `å\x8c\x97` | 响应头无 `charset`，HTTP 库按 ISO-8859-1 解 | `r.content.decode('utf-8','replace')`；**长度类判据不受影响，内容类判据全废** |
| **计数器漂移** | 两次响应长度不同，误判布尔差分 | 页面/接口有自增计数器 | 差分前先验基线稳定；跨基值重复 |
| **游客 token 会变** | 脚本隔天跑不通 | token 每次重启 App 重新签发 | 脚本里**先自动取 token**，不写死 |
| **误触写接口** | 数据库被改了 | 用通用 payload 全量扫 | 先建写接口黑名单；发现即停并声明足迹 |

## 十一、判据纪律

1. **阳性对照必做** —— 没通过阳性对照的"没找到"不算结论。
2. **单样本差异不算证据** —— 要求稳定复现 + 跨基值一致 + 至少一个带外信号。
3. **分页机制先于规模结论** —— 先证明能翻页，再谈能导多少。
4. **格式匹配 ≠ 字段性质** —— 见 §8.1。
5. **"没测到" ≠ "不存在"** —— 报告分三栏写：已验证的负面 / 明确未验证（含原因） / 方法缺陷。
6. **自己的操作足迹要主动报** —— 尤其误触写接口这类。

## 十二、报告结构（可直接套用）

```
一、执行摘要        —— 一句话结论 + 最高危项 + "数据能否用于登录"的专项结论
二、资产测绘        —— 网段/主机/指纹 + 基础设施澄清
三、漏洞清单        —— 按【客户端侧 / 后端 API 侧】分线，按级别排
四、重点漏洞详述    —— 每条: 端点 → 规模实测 → 判据验证 → 机制实测 → 影响 → 复现命令
五、攻击链          —— 按阶段，并说明"为什么止步于第N阶段"
六、专项验证        —— 如"泄漏数据能否登录"，逐项列表
七、已验证的防护有效项  ← 别省这章！评审会问"XX 测了吗"
八、未验证项与局限  —— 含方法缺陷，如实标注
九、整改建议        —— 按优先级分档
十、附录            —— 方法论、工具、PII 审计结果
```

**两条经验**：
- **第七章不能省。** 一份只写漏洞的报告，评委会问"跨租户测了吗""注入测了吗"。把负面结论摆出来，比被问出来强。
- **"为什么止步"要写。** 是没权限、是网络不通、还是防护有效 —— 三种原因性质完全不同，必须讲清。
